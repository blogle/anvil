Normative-ish vocabulary · v0.2

Small nouns. Hard edges.

This page says what Anvil should mean before it says how Anvil should run. “Must” marks a design constraint; “should” is a proposal awaiting a decision.

Canonical nouns

NounMeaningDoes not mean
CampaignA multi-repository objective and dependency graph.One issue, session, or PR.
CommissionOne independently integrable objective/change and its acceptance boundary. It is the one decision authority.An OpenCode Task or a GitHub issue.
AssignmentDelegated responsibility for a worker or role to advance a Commission.Proof that work happened.
AttemptA bounded strategy that may span sessions, with explicit start, stop, and outcome.A single session or turn.
CandidateA revision identified by code, base, and dependency identity.A branch name alone.
FindingA typed observation about the candidate or world, with severity and provenance.A model’s ungrounded suggestion.

DecisionA closed, inspectable control outcome selected by Commission policy.Sprawling early-return control flow.
OperationAn idempotency-scoped request to change an owned external system.A side effect hidden in observation.

Lific issues, OpenCode sessions/turns, and GitHub PRs are external objects. Anvil may reference them; it must not collapse them into an Anvil-owned Task noun.

Invariants
  1. A Commission has one active decision authority at a time. Workers propose; policy decides.
  2. World state is authoritative. Every reconciliation reads current remote state before selecting an Operation.
  3. Evidence is immutable and bound to a Candidate identity. Evidence from another revision cannot silently satisfy a gate.
  4. An implementer cannot unilaterally weaken acceptance criteria. Amendments are governed Commission decisions.
  5. At most one mutable writer owns a workspace at a time. Observation may be concurrent; mutation must have ownership.
  6. Every external mutation has an operation identity, an owner, an observable result, and a retry/recovery story. Exact semantics remain open.
  7. Fresh sessions reconstruct compact operational context from durable artifacts and observable state, not by cloning a long transcript.


Example lifecycle
Objective: update a shared SDLC contract across dotfiles and anvil.
  1. A Campaign graph records the two repositories and their dependency edge.
  2. A Commission defines the independently integrable contract change and acceptance checks.
  3. An Assignment gives a worker an Attempt with repository instructions, protocol, and current Finding hierarchy.
  4. OpenCode edits in a sandbox. Anvil observes session events, todos, tool results, Git, and CI without treating any one as proof.
  5. A watchdog can intervene before idle. Reconciliation emits a typed Decision: continue, refresh context, repair a finding, or escalate.
  6. A Candidate is created from an exact revision/base/dependency identity. Checks produce immutable Evidence.
  7. Only when gates hold does policy choose Integrate; otherwise it records the next bounded Attempt or Escalate.


Acceptance criteria for a useful v2
Required behavior
  • One can inspect current Campaign, Commission, Assignment, Attempt, Candidate, Findings, Evidence, Decisions, and Operations through an API.
  • A fresh worker session can start from a compact context packet and durable artifacts.
  • A dropped or duplicated observation does not create an untracked mutation.
  • Controller actions and status are inspectable and controllable without reading full transcripts.
Validation shape
  • Pure policy tests cover decisions and invariants.
  • Scenario/fault injection covers stale state, timeouts, duplicate events, and partial operations.
  • Contract tests use local OpenCode/Postgres doubles; narrow Kubernetes integration tests the real boundary.
  • An occasional affordable SWE-bench subset compares OpenCode baseline with Anvil; it is not a universal oracle.
